# 商业视频改款工作流

## 1. 项目输入

保存原视频、用户字幕稿、当前唯一目标产品的参考资产和权利状态。字幕稿是声音策略的输入，不等同于全片画外音。

## 2. 原片与字幕联合分析

1. 提取视频总览、音频、候选切镜帧。
2. 判断原片的人物说话、画外音和静默占比。
3. 按语义拆字幕段，标记信息、情绪和转化职责。
4. 形成钩子、产品承诺、视觉证据、吃后体验、结尾回报。
5. 为每段选择 `voiceover`、`on_screen_speech` 或 `silent` 并写理由。

人物直视镜头、原片已有自然讲话节奏、台词承担信任或体验表达时，可用人物讲话。台词解释产品细节而画面需要专注材质、手部或吃咬动作时，优先画外音。吃食者在实际咬合与闭口咀嚼区不做完整台词口型；咬合完成、产品离嘴后可以按原片节奏立刻接口播，原片没有吞咽或吃后反应时不补写。

## 2.5 跨项目资产盘点

在任何换脸、换产品、换包装、补图、重拆镜或 Word 返工生图前，盘点当前项目和用户点名的历史交付：

1. 从 `avatar_library.json` 查人物/换脸参考、授权范围与历史批准换脸帧。
2. 从 `product_bible.json`、`knowledge_index.json` 和逐镜资产链查产品/包装参考与历史批准换产品帧。
3. 查找 source-first、动作/美观候选、approved-first、分镜成品、旧 Word 内嵌图和对应 manifest。
4. 为每个新镜头比较人物、产品状态、包装数量、场景、构图、动作语义、画幅、字幕水印和像素质量，写入 `planning/asset_reuse_plan.json`。
5. 先以 `--stage pre-generation` 运行 `scripts/audit_asset_reuse.py`。能够复用时禁止生图；只有缺失、损坏、授权不符、无法安全整理画幅或像素 QA 不通过的镜头才允许补生，并逐镜记录原因。

参考资产只承担身份/结构知识，不能直接当交付帧；历史候选帧只有经用户授权和同等级 QA 提升为批准帧后才能进入 Word。人物与产品同时替换时分别绑定两个库层，禁止用一次“整图已批准”掩盖换脸或产品任一层失败。

## 3. 规划视觉结构

全片只使用：

- `product_showcase`：没有可识别人物，展示产品、断面、质地、摆放和受力反应。静物镜不出现手；纯手部掰开镜设置 `character.hands_only=true`，只允许动作所需双手。
- `person_product_showcase`：人物手持或指向产品、展示产品并可在合适时讲话。
- `person_eating`：咬下、产品离嘴与闭口咀嚼；吞咽和吃后反应仅在原片确实可见/可听或用户明确新增时出现。

占比没有固定万能答案。根据字幕的信息密度、原片风格和产品卖点设置范围并写入 `visual_mix_targets`。默认审查重点：产品证据不能太少，人物吃产品不能只出现一瞬，也不能重复咀嚼拖慢节奏。

### 原片分镜、4秒连续生成与吃食节奏

1. 先把原视频每个硬切和动作功能镜列为 `SRC001…`，保存准确起止秒数、原片分镜描述和首帧；禁止先按4秒生成规格粗暴重切。
2. 每个 `SRC` 必须在 `shots[].source_units` 中恰好出现一次，并拥有至少一张自己的批准目标帧；同一 SRC 跨越多个动作关键状态时可保留多张有序状态图，每张写独立职责。小于4秒的 `SRC` 只能与时间上相邻的 `SRC` 合并为一个不少于4秒的连续生成片段，不能删除、跳过、重复或为减少 Prompt 数而合并。
3. Word 同时显示原片准确秒数、合并后生成镜内秒数、按原片节奏和新版口播推算的分镜描述、对应口播稿与该 `SRC` 的图片。
4. 原视频总时长达到30秒时，先数原片已有吃食次数。已有3次或更多时新增0次；不足3次时只补 `3－原片次数`。新增吃食镜必须由新版口播与短视频节奏确定，分散在不同节奏点，中间至少隔一个非吃食片段；不得把三次排成连续镜头。所有新增镜头使用 `ADD…` 写入 `inserted_units`，保留生成镜内秒数、新增理由、节奏锚点、源片参考 ID/帧、口播和独立批准图；禁止给它编造原片秒数或塞进 `source_units`。
5. 吃食 Prompt 先继承原片送入口、张口、牙齿接触、产品离嘴、咬口、头部/视线和声音节奏。模板只补缺口。原片没有吞咽或吃后反应时不强加；咬合完成、产品离嘴后可马上说口播。

每个 `S` 可以只有 SRC、只有 ADD，或同时包含两者；总控按生成镜内时间合并两类 unit，要求从0.00连续覆盖整个 S，无空洞、无重叠。新增镜头的 `source_reference_frame` 是表演/构图依据，不得被称作“该镜原片首帧”，也不得用 S 的生成时间去源视频错误抽帧。
6. 黄油脆丝棒把掰开视为与吃食相同的节奏证据：可有人物出镜；同时至少有一个无脸、无头、无躯干的纯手部产品掰开镜。两类都必须为同一根一次咔嚓、少量真实掉渣、互补橙金断面和质量守恒。

## 4. 拆镜与帧

1. 按叙事和动作完整性拆独立生成片段。
2. 每个片段内部再拆 `action_beats`。
3. 从片段起始时间提取 `source_first_frame`。
4. 在片段内部提取多张 `beauty_keyframe_candidates`。
5. 单独选择 `selected_beauty_keyframe`。
6. 从真实首帧改图，实际绑定对应产品参考资产，完成产品原尺寸局部 QA 后才能保存为 `approved_generation_first_frame`。

包装镜在改图前还要按实际透视建立可见盒面清单。正面、侧面、顶面分别绑定批准母版；可读文字和图案使用单应性或确定性合成投射，生成模型只修盒体几何、折边、环境光、反光、接触影和边缘融合。自然遮挡或出框允许存在；可见区域缺字、乱码、镜像、跨边错位、被压缩或被重新排版一律拒收。

首帧负责生成连续性；美观帧负责风格和细节参考。两者不得混用。

## 5. 知识库与数字人

按镜头条件检索已批准知识条目，记录命中 ID 和版本。图片和 Prompt 条目都必须有适用条件。数字人素材只在用户明确选择且肖像授权通过后绑定。

## 6. 生成前检查

1. 字幕段全部分配到镜头。
2. 声音方式有原片与字幕依据。
3. 每镜只属于三类允许画面之一。
4. 场景支持该镜头叙事功能。
5. 产品、人物展示和人物吃产品的时长占比在规划范围内。
6. 开头有钩子，镜头时长和动作节拍不拖沓。
7. Prompt 包含场景、人物、情绪、动作、产品材质、摄影、灯光、声音和禁止项。
8. 分镜真实首帧、美观帧和改图首帧分开绑定。
9. 黄油脆丝棒裸产品不是贴图、浅浮雕、压花或光滑橙色棒体，局部与 `细节.jpg` 结构一致。
10. 黄油脆丝棒外盒锁定 `15 × 15 × 4.5 cm`、1:1 正面和约 0.3 边长盒厚，同框多盒同尺寸。
11. `story_plan.pacing` 同时保存目标总时长、平均镜长、单镜最长值和屏内/画外音语速上限。
12. 逐镜保存句段数、有效字符数、实际可说时段、字/秒和排除时段；入口、咬合、闭口咀嚼、吞咽、必要换气、纯拟音与无声观察不计入屏内口型容量。
13. 连续生成片段通常为4–8秒、句段≤3、屏内≤5.0字/秒、画外音≤5.5字/秒；项目可按源片与平台能力声明更长上限，但不得为时长、快速口播或字幕补足删掉任何 SRC。
14. 先通过节奏与时间容量审核；只有用户/平台明确启用时，再执行每镜 Prompt 3000–4000 字审核。不得为了字符下限、减少 Prompt 数量或沿用原片镜头数而合并镜头。
15. 用户要求复刻成片“每镜有口播”时，逐镜拒绝空口播和纯静默镜头；但实际可说时段必须扣除语义换气、对方反应、实际咬合、实际闭口咀嚼、原片确有的吞咽、掰断、撕袋和关键拟音窗口。人物镜头还须有动作或互动链，不能只站定介绍。若只能靠抹掉喘息或持续提速容纳文本，标记 `BREATHLESS_SPEECH_PACKING` 并先重分句、改画外音或按原切点拆镜。
16. 对照 `source/source_manifest.json.source_shots` 核对覆盖率必须为100%，顺序一致、无重复；逐个 `SRC` 的图片、原片秒数、生成镜内秒数、分镜描述和口播稿均非空。
17. 对照吃食/掰开计划核对全部 `ADD`：每个计划中的新增事件都命中唯一 `inserted_shot_id`，并有独立批准图、可编辑描述、生成秒数、口播、新增理由、节奏锚点和源片依据；计划外 ADD 与没有 ADD 卡的 inserted occurrence 都阻断。
18. 原片≥30秒时核对吃食计划的来源数、补入数与目标数；新增吃食点不相邻，不以“模板更香”为由覆盖原片表演。
19. 锁定新版口播全文和程序实算字符数；按生成时间拼接全部 SRC/ADD 卡的口播，再按 S 顺序拼接所有有声 `audio.script_text`，两者都必须与全文等价。缺字、重复、文字截图或虚假字数不得进入 Word。
20. 黄油脆丝棒至少有一个 `hands_only_product` 掰开点；单次咔嚓、断面、掉渣和质量守恒均为结构化必填项。
21. 包装镜逐盒核对实际可见区域与对应母版；不要把自然出框误判为缺图，也不要为了露全图案而缩小包装。

## 7. 编译、生成后审核与交付

通过 lint 后编译逐镜 Prompt、生成包、交付回执和短分镜确认卡。`prompt_only` 只跳过批准生成首帧、候选图片与成品像素 QA，故事、角色、SRC/ADD、六层证据、无缝动作节拍、口播、产品物理和包装母版结构仍走同一硬门禁；汇总稿必须由编译器从同批 `Sxxx.md` 逐字生成。运行 `pipeline.py verify-prompt-delivery` 返回 `authorized` 前，不得把任何 Prompt 称为完成或可交付。用户提供即梦结果时继续抽查关键时点并做差异审核；产品结构、包装尺寸、人物身份、手嘴接触或状态连续性失败时，只重做失败镜。不得在失败生成图或失败视频上叠修。

Word 导出前重跑 lint，并用 generation pack 的 `compile_id`、canonical input hashes、Prompt 文件哈希及历史 input snapshot 证明所有输入来自同一编译批次；再以 `--stage pre-word` 运行资产复用审核。实际 owner 图片出现数必须等于全部 SRC/ADD 的有序 `delivery_asset_ids` 总长度，另加显式登记的连续边界参考出现数；逐张是独立9:16文件，不得用拼图、重复图、源视频占位帧或参考库图片冒充。不同 unit 默认禁止共享同一 asset ID、路径或实际 SHA-256；同一 owner 图在相邻生成段边界重复展示时仍以真实 owner caption 登记，不计作另一个 unit 的覆盖。导出后由只读 aligner 逐 unit 沿 OOXML relationship 核对图片实际字节、顺序、asset ID、owner 与职责。用户侧只交付渲染检查通过的 DOCX；TXT、JSON、manifest、对齐报告和图/文分支 handoff 保留在项目内部，不发给用户，也不在最终回复中列出。
